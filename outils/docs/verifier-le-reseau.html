Comment vérifier que rien ne sort du poste

« Aucune donnée ne quitte le poste » est une promesse. Cette page dit comment la vérifier soi-même, en quinze minutes, sans rien nous demander. Version {{VERSION}}.

1. Le plus simple : le câble débranché

Coupez le réseau du poste (câble, Wi-Fi, ou « Mode Avion »), ouvrez l'application, ouvrez un PDF, corrigez-le, caviardez un mot, lancez la reconnaissance de texte sur un scan, enregistrez. Tout fonctionne : l'application n'a besoin de rien d'extérieur — ni pour s'ouvrir, ni pour la reconnaissance de texte (le moteur et les modèles de langue français et allemand sont dans le dossier), ni pour les polices, ni pour la licence (un fichier signé, vérifié sur le poste). Ce que la personne ne peut pas faire sans réseau — envoyer un courriel — n'est pas une fonction de l'application.

2. Regarder ce que le poste émet

  1. Sur un poste d'essai, lancez un observateur de connexions au choix : Moniteur de ressources › Réseau › Connexions TCP (intégré à Windows), TCPView ou Process Monitor (Sysinternals), le journal du pare-feu Windows (Pare-feu avec fonctions avancées de sécurité › Propriétés › Journalisation : « journaliser les paquets ignorés » et « les connexions réussies »), ou la journalisation du pare-feu périmétrique de la commune.
  2. Filtrez sur le processus AktumPDF.exe (l'application lance aussi des processus enfants du même nom : moteur d'affichage, moteur graphique).
  3. Travaillez une quinzaine de minutes comme une secrétaire : ouvrir, corriger, caviarder, reconnaître le texte, imprimer, enregistrer, fermer.
  4. Résultat attendu : aucune connexion sortante vers une adresse autre que 127.0.0.1 (la boucle locale du poste). Le moteur d'affichage tente parfois d'ouvrir un port local ; ce n'est pas du réseau.

L'application n'ouvre aucun port en écoute : le pare-feu n'a rien à autoriser (§10 du guide d'administration).

3. Pourquoi elle ne peut pas, même par erreur

Trois barrières, indépendantes — chacune suffit pour une défaillance des deux autres. Elles sont écrites dans desktop/main.js, dont le texte est public (dépôt de l'éditeur) ; voici ce qu'elles font, en trois lignes :

BarrièreL'extraitCe qui en résulte
Les noms de domaine ne se résolvent pasappendSwitch('host-resolver-rules', 'MAP * ~NOTFOUND , EXCLUDE 127.0.0.1')Toute adresse qui n'est pas la boucle locale échoue avant qu'un paquet ne parte.
Un mandataire fixe et mort sert toutes les sessionsappendSwitch('proxy-server', '127.0.0.1:1')Pas de mandataire du système, pas de détection automatique (WPAD/PAC) : ce qui échapperait au résolveur tombe sur un port fermé.
Chaque session refuse toute requête non localesession.webRequest.onBeforeRequest(…)La requête est annulée et comptée, pour que le test puisse dire combien en ont été tentées (zéro).

De plus, la page de l'application porte une politique de sécurité (default-src 'none'; connect-src blob: data:) qui interdit au navigateur lui-même d'ouvrir une connexion ; aucun composant n'est chargé depuis Internet (la construction échoue si une adresse réseau réapparaît dans le code livré). Le moteur d'affichage est lancé avec ses services en ligne éteints (mises à jour de composants, signalements, synchronisation).

4. Ce que l'éditeur observe à chaque version

Dans l'application empaquetée : elle est lancée derrière un mandataire d'observation qui note toute connexion qui lui parvient ; elle est utilisée pour de vrai (ouvrir, modifier, enregistrer, reconnaître le texte d'une image) ; le test échoue à la moindre connexion. Il commence par lever les barrières pour montrer que l'observateur voit ce qui s'échapperait (deux appels d'essai, http et https), puis les referme : rien n'arrive. C'est desktop/reseau-test.js, lisible et rejouable.

Dans la page : la suite de bout en bout tente, depuis la page, six formes d'envoi vers une adresse inexistante — requête directe (fetch), XMLHttpRequest, image, WebSocket, balise d'envoi, formulaire — et exige que la politique de sécurité de la page les refuse toutes avant qu'un paquet ne parte (test-e2e/reseau-page.spec.js).

5. Ce que cette vérification ne couvre pas

  • Un poste compromis par ailleurs, ou un composant du système : l'imprimante, le client de messagerie que la personne utilise pour joindre un fichier, un antivirus qui envoie des fichiers à son éditeur.
  • La page d'essai en ligne du site de l'éditeur, qui charge ses composants depuis Internet et n'est pas destinée à des documents réels (elle le dit à l'ouverture). Elle n'est pas dans l'archive.
  • L'attestation d'un tiers : une capture de trafic par un bureau d'ingénieurs indépendant n'a pas encore été établie ; si votre marché l'exige, demandez-la : l'éditeur la fera faire sur la version que vous achetez.
